CORE THINKING MODEL TO RESPECT:
We are building a database-driven, process-driven, metadata-driven ERP kernel.
In this model:
- business structure should be governed as data
- process behavior should be governed as data/metadata
- UI surfaces should be governed as data/metadata
- code should remain the generic runtime and helper layer
- the system must avoid rigid hardcoded ERP structure

IMPORTANT PRINCIPLE:
Even “actions” like knitting 200 kilos of fabric are still part of governed business data and process semantics.
The database should govern:
- what the process is
- what the task means
- what macro is used
- what effect is allowed
- what service object/service object category applies
- what headers/structure are valid
Code should not silently become the real source of truth for these semantics.

PRIMARY ARCHITECTURE MODEL:
1. process
2. task label
3. macro
4. effect library
5. service object + service object category runtime parameters

RULES:
- process authority must remain DB-driven
- macro authority must remain governed
- effect library definition/governance should not remain hidden in hardcoded JS beyond what is unavoidable for runtime dispatch
- handler implementations may remain in code
- effect catalog, effect scope, allowed params, service object applicability, and governance should move toward explicit governed structures
- document handling must not remain under-modeled or hidden behind accidental generic behavior
- routes must remain transport-only
- UI behavior must remain engine-/surface-driven
- no route/module should become hidden business authority
